# Bitácora de desarrollo

Registro cronológico de avances técnicos del proyecto **NS PAC Integration Facturama**.

### 2026-08-07 — Resumen inicial de la integración NetSuite–Facturama

- **Estado:** pendiente de validación
- **Objetivo o problema:** Implementar un método de envío de E-Documents que conecte NetSuite con Facturama API-Lite para timbrar CFDI 4.0, recuperar el XML certificado y actualizar la transacción de origen.
- **Cambios realizados:** Se inicializó un proyecto SDF de tipo Account Customization y se incorporó un plug-in de envío en SuiteScript 2.0. El flujo implementado recibe el JSON generado por la plantilla de E-Document, obtiene la configuración del PAC por subsidiaria, autentica la petición, solicita el timbrado, descarga y guarda el XML, actualiza campos de certificación CFDI y genera/adjunta un PDF. El repositorio conserva una versión monolítica de fase inicial y una versión modular separada por configuración, API, manejo de archivos y actualización fiscal. También incluye registros personalizados para configuración y logging, plantillas FreeMarker, payloads de ejemplo y material técnico de referencia.
- **Archivos o componentes:** `pac_facturama_integration/src/manifest.xml`; `pac_facturama_integration/src/FileCabinet/SuiteScripts/Facturama_Integration/pi_sads_fama_connector.js`; `pi_sads_fama_encapsulado.js`; módulos `lib/sads_fama_config.js`, `lib/sads_fama_api.js`, `lib/sads_fama_files.js` y `lib/sads_fama_cfdi.js`; objetos SDF `customrecord_sads_fama_config` y `customrecord_sads_fama_logger`; recursos de análisis y prueba bajo `Tests/`.
- **Evidencia:** Commit inicial [`999df9c`](https://github.com/saulkgames/NS_PAC_Integration_Facturama/commit/999df9cc28e2ba1a8fc545e6b7a4b221a34ce73c), fechado el 2026-08-01, con 80 archivos. Inspección del manifiesto SDF, los dos plug-ins, cuatro módulos principales y los dos registros personalizados. No se encontraron pull requests ni incidencias en GitHub.
- **Resultado:** Existe una base funcional por inspección de código para un procesamiento síncrono de timbrado, descarga del XML, actualización de campos CFDI y generación de PDF. No hay evidencia registrada de despliegue SDF, ejecución end-to-end, CFDI timbrado exitosamente ni medición de gobernanza; por ello el avance no se considera validado en cuenta.
- **Decisiones técnicas:** La implementación modular separa responsabilidades de configuración, comunicación HTTP, persistencia de archivos y actualización fiscal. La configuración se resuelve por subsidiaria mediante un custom record y el plug-in reporta el procesamiento del PAC como síncrono.
- **Problemas y riesgos:** Coexisten dos implementaciones del plug-in y falta confirmar cuál debe desplegarse. El módulo de archivos mantiene un ID de carpeta marcado como pendiente de configuración. La variante monolítica registra payloads y respuestas completas, lo que requiere revisar permisos, retención y redacción de datos fiscales. Las credenciales del PAC dependen de un registro personalizado y deben validarse sus permisos y protección en NetSuite. El consumo de unidades de gobernanza del flujo síncrono aún no está medido.
- **Pendientes:** Definir el plug-in definitivo; parametrizar la carpeta de XML/PDF; revisar la seguridad del registro de configuración y del logger; ejecutar validación en sandbox con datos controlados; comprobar timbrado, XML, PDF y campos CFDI; documentar despliegue, roles/permisos, resultados de prueba y consumo de gobernanza.
- **Referencias:** Repositorio [`saulkgames/NS_PAC_Integration_Facturama`](https://github.com/saulkgames/NS_PAC_Integration_Facturama), rama `main`.

### 2026-08-07 — Timbrado de Cash Sale y ajustes de estado y auditoría

- **Estado:** pendiente de validación
- **Objetivo o problema:** Completar la fase inicial del Sending Method para timbrar ventas de contado mediante Facturama y lograr que NetSuite actualice correctamente los campos, el estado y el Historial de Auditoría del documento electrónico.
- **Cambios realizados:** Se amplió el orquestador SuiteScript 2.0 para crear eventos en el Audit Trail nativo, devolver al framework un resultado estructurado con estado de éxito o error y entregar campos adicionales para actualización. El módulo de API ahora realiza parseo seguro de respuestas, timbrado por `POST` y descarga del XML por `GET`. El mapeo CFDI incorporó UUID, fecha de certificación, sellos, serie, folio, QR, fecha de emisión y número de serie del CSD, con recuperación alternativa desde el XML. El guardado de archivos decodifica el contenido Base64 recibido del PAC y usa la carpeta estándar de adjuntos. Se agregó un logger modular y la búsqueda de configuración excluye registros inactivos.
- **Archivos o componentes:** `pi_sads_fama_connector.js`; módulos `lib/sads_fama_api.js`, `lib/sads_fama_cfdi.js`, `lib/sads_fama_config.js`, `lib/sads_fama_files.js` y el nuevo `lib/sads_fama_logger.js`; notas y utilidades de prueba bajo `Tests/`. También se retiraron del proyecto SDF `customrecord_sads_fama_config.xml` y `customrecord_sads_fama_logger.xml`.
- **Evidencia:** Commit [`3322e51`](https://github.com/saulkgames/NS_PAC_Integration_Facturama/commit/3322e5138ab4793baa7d013b13c1280c07a02376), con 13 archivos afectados. El mensaje del commit reporta que el Sending Method conecta y timbra y que la plantilla de Cash Sale funciona. Se agregaron `Tests/Factura_Timbrada.xml` y `Tests/campos_edoc_crtified.png` como artefactos de prueba. El merge [`cb65f02`](https://github.com/saulkgames/NS_PAC_Integration_Facturama/commit/cb65f026bf3fcb12f26ce6a14cf9fc4b45490337) integró estos cambios con la bitácora. No se encontraron pull requests ni incidencias asociadas.
- **Resultado:** Se cuenta con evidencia reportada de conexión y timbrado de una Cash Sale, además de artefactos de prueba. La actualización correcta del estado del documento electrónico y del Audit Trail aún no está confirmada. La inspección del código actual detectó una incompatibilidad entre el conector, que invoca `getFieldsToUpdate`, y el módulo CFDI, que solo exporta `updateTransaction`; por ello el flujo vigente requiere una nueva prueba antes de considerarse completado.
- **Decisiones técnicas:** Se optó por escribir un evento explícito en `customrecord_psg_ei_audit_trail` y devolver `eiStatus` con `extraFieldsForUpdate` al framework. Si el PAC timbra pero falla la actualización local, el módulo genera una alerta que conserva el UUID e indica no volver a timbrar, reduciendo el riesgo de duplicidad fiscal.
- **Problemas y riesgos:** Sigue pendiente confirmar los códigos de estado y evento esperados por el framework de E-Documents. Los dos custom records propios fueron retirados del SDF aunque el código continúa dependiendo de ellos, por lo que debe definirse si existirán como prerrequisito o volverán a versionarse. El destino de archivos permanece ligado al ID interno `-15`. `Tests/Factura_Timbrada.xml` contiene una exportación/respuesta extensa de NetSuite con campos operativos y potencialmente sensibles; no se copiaron sus valores a esta bitácora y debe revisarse su sanitización o retiro. El logger puede almacenar detalles fiscales o técnicos y requiere permisos y política de retención adecuados.
- **Pendientes:** Corregir y alinear la interfaz entre el conector y `sads_fama_cfdi.js`; repetir la prueba de Cash Sale desde el código actual; confirmar estados, botones, PDF e Historial de Auditoría; definir la propiedad SDF de los custom records; sanitizar los artefactos de prueba; validar envío por correo, roles/permisos y consumo de gobernanza.
- **Referencias:** Comparación de `main` entre [`4c4b093...cb65f02`](https://github.com/saulkgames/NS_PAC_Integration_Facturama/compare/4c4b0937a3274abf13891f84e5293e63315be83b...cb65f026bf3fcb12f26ce6a14cf9fc4b45490337).
